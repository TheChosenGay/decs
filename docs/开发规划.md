# 查询与并行开发规划

本文记录后续要实现的联合查询、数据并行和系统并行。当前代码先保持单组件串行查询，按下面的阶段往上加，不把几层并行混进同一个循环。

## 现状

查询入口在 `World`，存储是 `Storage` 里的 `HashMap<TypeId, Box<dyn ErasedDenseSet>>`。每个组件一套 `DenseSet<T>`：

- `sparse`：entity id 到 dense 下标
- `dense`：组件值，连续存放
- `dense_sparse_map_arr`：dense 下标对应的 entity id

`query` / `query_mut` 只接受一个组件类型，逐个实体调用闭包。`#[derive(Component)]` 只生成空的 `impl Component`。

后续要动到的约束：

- `Entity.generation` 现在是 `Cell<u32>`。`Cell` 不是 `Sync`，所以 `Entity` 不是 `Sync`，`Storage.entities` 不能跨线程共享。
- `ErasedDenseSet` 没有 `Send + Sync`，擦除后的集合不能交给线程池。
- 闭包是逐元素的，编译器很难稳定向量化。

## 三层分开

| 层 | 解决什么 | 并行粒度 | 本阶段是否做 |
| --- | --- | --- | --- |
| 联合查询 | 一次取出多个组件 | 无，先串行 | 先做 |
| 数据并行 | 同一个查询切给多个线程 | 一个查询内部的 dense 切片 | 联合查询稳定后做 |
| 系统并行 | 多个互不冲突的查询同时跑 | System 与 System 之间 | 数据并行之后做 |
| SIMD | 同一段连续数据批量计算 | 一个 chunk 内部的向量指令 | 有基准证明热点后再做 |

数据并行和系统并行是两件事，可以叠在一起：调度器先挑出互不冲突的 System，每个 System 再对自己的驱动集合做分块。第一版只做数据并行。

## 目标接口

联合查询用元组表达借用：

```rust
world.query::<(&Position, &Velocity)>()
    .for_each(|entity, (position, velocity)| { /* ... */ });

world.query::<(&mut Position, &Velocity, &Health)>()
    .for_each(|entity, (position, velocity, health)| { /* ... */ });
```

数据并行是同一套查询上的另一种执行方式：

```rust
world.query::<(&mut Position, &Velocity)>()
    .par_for_each(|entity, (position, velocity)| { /* ... */ });
```

可选过滤后置，不进第一版：

```rust
world.query::<(&Position, &Velocity, Option<&Health>)>()
```

现有的 `query::<T>` / `query_mut::<T>` 保留，内部改成走新查询，调用方不用改。

## 阶段 1：串行联合查询

### Query 与 Fetch

`Query` 描述用户要取什么，`Fetch` 描述已经拿到存储之后怎么按 entity id 取出引用。

- `Query`：组件组合、读写集合、选哪个 `DenseSet` 当驱动集。
- `Fetch`：对一个 entity id 做 sparse 查找，返回 `Option<(&A, &B, ...)>`。查找失败表示这个实体缺组件，跳过。

`World::query` 只负责借出存储并驱动循环，不自己写每种元组的匹配逻辑。

遍历规则：

1. 在参与查询的集合里，选 `dense.len()` 最小的那个当驱动集。
2. 顺序扫驱动集的 `(entity id, 组件)`。
3. 用这个 entity id 到其余集合的 `sparse` 里探测。全部命中才调用闭包。

查询期间禁止增删实体和组件。第一版闭包签名保持 `FnMut`，不把 `World` 传进闭包。

### 元组实现

Rust 没有任意长度元组的泛型实现，所以在 `decs` 内部用 `macro_rules!` 生成固定档位：

- `(&A,)` 或直接复用现有单组件查询
- `(&A, &B)`
- 一直到 8 项

这里的宏和 `decs-macro` 的 `#[derive(Component)]` 无关。派生宏继续只负责 `impl Component`。

每一项可以是 `&T` 或 `&mut T`。同一查询里同一个组件不能出现两次。两个可变组件第一版允许串行查询，不允许数据并行。

### 完成标准

- `(&Position, &Velocity)` 只命中同时拥有两者的实体。
- 缺一个组件的实体被跳过，不 panic。
- 驱动集换成另一个组件后，命中集合不变。
- 单组件旧 API 行为不变。
- 有测试覆盖：双组件、三组件、空结果、驱动集切换。

## 阶段 2：实体与存储变成可共享

数据并行之前先改这几处，否则线程池过不了 `Sync`。

`Entity` 改成普通字段：

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub struct Entity {
    pub(crate) id: u32,
    pub(crate) generation: u32,
}
```

generation 只在回收时增加。`recycle_entity` 拿到的是所有权，直接 `entity.generation += 1` 再放回空闲队列。序列化如果还要保留，继续走 `serde`，不再依赖 `Cell`。

`Component` 改为：

```rust
pub trait Component: Send + Sync + 'static {}
```

`ErasedDenseSet: Send + Sync`。`DenseSet<T>` 在 `T: Send + Sync` 时自动满足。

这一阶段还不加 Rayon，先让 `cargo test` 和现有 example 在新 `Entity` 上通过。

## 阶段 3：单个查询的数据并行

并行单元是驱动集的 dense 切片，不是把整个 `World` 拆开，也不是按 archetype 分块。

只支持这两种组合：

- 全部只读，例如 `(&Position, &Velocity)`。
- 恰好一个可变组件，并且它就是驱动集，例如 `(&mut Position, &Velocity)`。

`(&mut Position, &mut Velocity)` 继续只走串行。两个可变集合都按 entity id 随机访问，动态 `HashMap` 里很难证明每个线程碰到的元素互不重叠。

执行方式：

1. 规划阶段确定驱动集和其余只读集。
2. 把驱动集的 entity id 切片和值切片按相同边界切开。
3. 每个 worker 独占自己的 `&mut [T]`，对其余组件只拿共享引用。
4. worker 内部仍是「id → sparse 探测 → 调用闭包」。

依赖用 `rayon`。默认用 `par_iter` / `par_chunks`，让 Rayon 选粒度。chunk 大小先不暴露到公开 API；基准证明有收益再加 `par_chunks(n)`。

`par_for_each` 的闭包是 `Fn + Sync`，不能像串行版那样带 `FnMut` 的外部可变状态。需要累加时，调用方用分线程局部结果再合并，或者继续用串行 `for_each`。

### 完成标准

- 只读联合查询和单可变联合查询的命中结果与串行一致，顺序不保证。
- 两个可变组件调用 `par_for_each` 时编译失败，或返回明确的规划错误。编译期拒绝优先。
- 用现有 `bench_query_fair` / `bench_traversal` 加一组并行对照，确认大 `n` 下有加速，小 `n` 不比串行差一个数量级。小数据可以内部退回串行。

## 阶段 4：系统并行

这一层调度的是多个查询，不再切同一个 dense 数组。

每个 System 在注册时声明访问：

```rust
struct Access {
    reads: BitSet,
    writes: BitSet,
}
```

组件在注册时分配连续编号，bitset 按这个编号置位。不要在每帧用 `HashSet<TypeId>` 做冲突计算。

两个 System 可以同时跑，当且仅当：

- `A.writes` 与 `B.reads` 不相交
- `A.writes` 与 `B.writes` 不相交
- `A.reads` 与 `B.writes` 不相交

冲突的 System 放进不同批次，批与批之间串行。同一批内部各自还可以做阶段 3 的数据并行。

System 先做成显式注册，不引入完整的依赖 DAG。调用顺序只保证：有冲突的后者不会和前者重叠执行。没有冲突的相对顺序第一版不保证。

### 完成标准

- 写 `Position` 与读 `Position` 被分到不同批次。
- 写 `Position` 与写 `Health` 可以同批。
- 批次划分有单元测试，不依赖真实线程时序。

## 阶段 5：SIMD

等阶段 3 的基准指出热点再做。Sparse set 联接是按 id 随机 gather，直接对联合查询上 SIMD 收益通常有限。

接口和逐元素闭包分开：

```rust
world.batch::<(&mut Position, &Velocity)>()
    .for_each_chunk(simd_kernel);
```

内核收到的是对齐过的切片，而不是单个 `&mut T`。实现顺序：

1. 先写标量 chunk 内核，看编译器能不能自动向量化。
2. 热点仍在算术而查找不再占主导时，再选 `wide` 或 `std::arch`。
3. 若随机 gather 成为上限，再单开存储方案：同一批实体的数值字段改成 SoA。那是存储层变更，不塞进现在的 `Fetch`。

## 明确不做

这些留在对应阶段之外，避免第一版范围膨胀：

- 查询过程中创建、删除实体或增删组件。
- 第一版的 `Without<T>`、变更检测、关系、事件。
- 在 `HashMap<TypeId, Box<dyn ErasedDenseSet>>` 上做多可变数据并行。
- 为了 SIMD 先把存储改成 archetype。archetype / SoA 只在阶段 5 的基准要求时另立设计。

## 建议落地顺序

1. 阶段 1：`Query` / `Fetch`、2～8 元组、串行联合查询、测试。
2. 阶段 2：去掉 `Cell`，收紧 `Send + Sync`，旧测试和 example 通过。
3. 阶段 3：`par_for_each` 与并行基准。
4. 阶段 4：`Access` bitset 和 System 批次。
5. 阶段 5：按基准决定要不要 chunk 内核和 SoA。
